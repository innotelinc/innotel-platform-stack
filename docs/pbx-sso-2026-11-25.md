# FreePBX administration now signs in with Cerulean Authentik — 2026-11-25

The FreePBX 17 administration GUI no longer asks for a FreePBX password on any public
name, and there is no standing password form on the container's port either. A request
on the edge is authenticated by Authentik, and the identity Authentik establishes is
what FreePBX uses. The only way to see the local form is for root to arm a flag inside
the container, and that flag lives in tmpfs.

## Why it was not working before

Two faults, either of which alone would have shown the password form:

1. `voice.innotel.site` forwarded to `192.168.1.52:8201`, a port nothing has ever
   listened on. The Authentik gate passed, and the post-login request died
   upstream. Fixed first (now `:8083`, the FreePBX Apache).
2. The gate authenticated but never passed the identity. NPM writes
   `advanced_config` at **server** level, and its generated `location /` sets its
   own `proxy_set_header` lines, so nginx does not inherit the server-level
   `X-authentik-*` headers into the location. FreePBX's SSO shim therefore saw
   no user at all and fell through to its login form. This affected every host
   using the managed gate, not just the PBX.

## What FreePBX does now

`/var/www/html/admin/libraries/gui_auth.php` (in the `freepbx-www` volume) reads
the identity the edge forwarded and opens the GUI without a password:

- A username in `sso_identities.php`'s `users` map, or a member of a group in its
  `groups` map, is opened as that FreePBX account. The maps currently resolve
  `dhunter` and every member of `authentik Admins` (`akadmin`, `dhunter`, `admin`)
  to the FreePBX `admin` account.
- A request that arrives **from the edge** with no identity, or with one that maps
  to nothing, gets a 403 page that names Authentik and the group to ask for. It
  does **not** get the password form.
- A request that arrives on the container's own address is untouched by the SSO
  block, but the password form is no longer a standing door there either (see
  *Break-glass* below).
- All the SSO code only runs when `REMOTE_ADDR` is the NPM edge (`192.168.1.71`).

The 403 that refuses an unmapped identity must be guarded by
`empty($_SESSION['AMP_user'])`. Without that guard the shim authenticates the request,
sets the session, and then 403s it anyway — a total lockout that looks exactly like
"no identity arrived". That mistake was made and fixed on 2026-11-25, and
`scripts/check-pbx-sso.py` now asserts the guard is still there.

### Break-glass

The stock password form is reachable only when root arms a flag inside the container:

```sh
docker exec freepbx-qvifit87vftfxd9ejsch2vxy touch /run/freepbx-sso-break-glass
# ... sign in on http://192.168.1.52:8083/admin/config.php ...
docker exec freepbx-qvifit87vftfxd9ejsch2vxy rm -f /run/freepbx-sso-break-glass
```

`/run` is the container's tmpfs, so a restart disarms it. Leave it disarmed: the
drift check warns when it is armed, because an armed flag is a password door open to
the LAN.

Backups from this change, beside the file: `gui_auth.php.bak-sso-edge-20261125` (the
first SSO version, with the form), `gui_auth.php.bak-sso-nopw-20261125` (form removed,
but the 403 was unguarded — the lockout), and
`gui_auth.php.bak-sso-breakglassguard-20261125` (immediately before the guard fix).

### `pbx.innotel.site` uses its own outpost

The other names use their domain's zone provider. `pbx.innotel.site` cannot: the zone
provider (`Innotel.site Zone`, provider 69) is a domain-level provider for
`*.innotel.site`, and it shadows every single-application provider for that name no
matter how the outpost provider list is ordered. Domain mode also cannot enforce a
per-application policy — Authentik only applies bindings in single-application mode.

So the console has both:

- provider **73** `Innotel PBX Console NPM Forward Auth` (`forward_single`,
  `external_host https://pbx.innotel.site`, `internal_host http://192.168.1.52:8097`)
  and app `innotel-pbx-console`, bound to `authentik Admins` (binding
  `8067566f-1d03-484a-86dc-ad83804c39a7`);
- a dedicated external outpost, container `authentik-pbx-outpost` on `192.168.1.71`
  (`ghcr.io/goauthentik/proxy:2026.8.6`, network `proxy_default`, no published
  ports), which carries **only** provider 73. NPM host 410 points its
  `/outpost.goauthentik.io` location and its sign-in redirect at that outpost.

That separation is what makes the group binding effective: a signed-in user outside
`authentik Admins` is refused at the authorize page, and an admin gets the console.

The outpost's API token is at `192.168.1.71:/root/.authentik-pbx-outpost-token`
(600, identifier `ak-outpost-fbd22a38-8b46-49a9-9b99-ac46c51d1f9b-api`). If the
container is lost, recreate it from that token rather than making a new outpost —
provider 73 and NPM refer to it by outpost identity.

## `:8083` is LAN-only

The published port is still how the edge reaches FreePBX, and it is also the
break-glass address. It is filtered on the PBX host (`192.168.1.52`) in **`raw
PREROUTING`**:

```
-A PREROUTING -s 192.168.1.0/24 -p tcp --dport 8083 -j RETURN
-A PREROUTING -s 127.0.0.0/8    -p tcp --dport 8083 -j RETURN
-A PREROUTING -p tcp --dport 8083 -j DROP
```

`raw PREROUTING` rather than `DOCKER-USER`: by `DOCKER-USER` the published port has
already been DNATed to the container's `:80`, so `--dport 8083` no longer matches and
a rule there silently allows everything. The rules are written by
`/usr/local/sbin/capstone-wan-acl.sh` and re-applied by the enabled one-shot
`capstone-wan-acl.service`, so a reboot restores them.

## Watching it

`scripts/check-pbx-sso.py` fails when any of this drifts. It reads NPM's rows (not the
files NPM regenerates), the shim inside the FreePBX container, and `raw PREROUTING` on
the PBX host:

```sh
./scripts/check-pbx-sso.py                       # on the edge
./scripts/check-pbx-sso.py --npm-url http://192.168.1.71:81 \
    --token-file /root/.npm-token --pbx 192.168.1.52 --ssh-key /root/.ssh/id_ed25519
```

Exit 0 = everything holds, 1 = drift, 2 = a host could not be read. It is listed in
`estate-checks.service` as `pbx_sso` and publishes the shared `innotel_estate_check_*`
family, so `EstateCheckAbsent`, `EstateCheckFailing` and `EstateCheckNotRunning` cover it
and the `Checks reporting` panel counts it. It installs with the unit, from `main` —
`check-installed-checks` compares the directory against `origin/main`, so installing it
ahead of the merge is itself reported as drift, and is what that alarm is for.

## The console's AMI link (2026-11-25)

`pbx.innotel.site` showed "Simulated · AMI connection closed" while every door answered.
Three separate things have to hold for it to say otherwise, and none of them lives in
this repository:

- **the `ami-bridge` sidecar.** Asterisk's manager binds `127.0.0.1` inside the FreePBX
  container, so the published `192.168.1.52:5038` lands on `15038` with nothing behind it.
  `alpine/socat` shares FreePBX's network namespace and forwards `15038 → 127.0.0.1:5038`.
  A redeploy that stops early leaves that container `Created` while FreePBX itself comes
  up healthy, and a restart of FreePBX leaves it `Up` in FreePBX's *previous* network
  namespace — still listening, forwarding into a sandbox Asterisk has left. Both happened
  during this work, and both read as "AMI connection closed" on the page, which is why the
  check looks at the sidecar's namespace and the wire, not only at the console. The repair
  is `docker compose up -d --no-deps ami-bridge` in the service directory.
- **the console's settings**, in its SQLite volume: `ami_host` is the host, not a compose
  DNS name (the console is on a different compose network and cannot resolve `freepbx`),
  and `ami_port`/`ami_user`/`ami_secret` are the manager user's. `PUT /api/settings`
  needs the `X-CSRF` header from the `ac_csrf` cookie; without it the console answers 403
  and the old values stay.
- **the console's client**, which reconnects on its own and reports `ami.connected` and
  `lastError` in `/api/dashboard` — the values the page renders.

`scripts/check-pbx-console.py` asserts all three: the sidecar running, the stored settings
naming the PBX and a manager user, an AMI login accepted on that host and port with those
credentials, and `ami.connected: true` with no `lastError`. It reads the console's admin
password from its own container environment over ssh, so no new secret is stored and the
check logs in the way the page does.

## Break-glass drill (2026-11-25)

The gate was made unreachable for one name only: `pbx.telno.services`'s
`/outpost.goauthentik.io` location was pointed at a closed port (`127.0.0.1:9`) through
the NPM API, measured, and put back. Every other name kept its own outpost throughout.

| what was tried | what came back |
| --- | --- |
| `https://pbx.telno.services/admin/config.php`, gate unreachable | `500` — no password form, no FreePBX page |
| `http://192.168.1.52:8083/admin/config.php`, flag absent | `403` |
| same, with `/run/freepbx-sso-break-glass` touched | `200`, the FreePBX password form |
| same, flag removed again | `403` |
| gate restored, anonymous request | `302` to Authentik |

So an unreachable outpost fails closed: the edge answers `500`, never the form, and the
only way in is the LAN flag that `check-pbx-sso.py` asserts is off. `500` is ugly; it is
also the only status nginx can return when an `auth_request` subrequest cannot be made,
and it is strictly better than a login prompt. The LAN path was proven on the PBX host
itself, which is what "the edge is down" leaves a person with.

`scripts/drill-pbx-breakglass.py` repeats these five measurements for one name, restores
the NPM row in a `finally`, and exits non-zero if any of them changes. Run it after an NPM
or FreePBX upgrade, or before trusting this document again.

It is scheduled: `systemd/pbx-breakglass-drill.timer` fires on the first of each month at
04:40 (`Persistent=true`, so a reboot does not skip the date) and the service runs it from
the edge, where the NPM token and the key to the PBX both live. Proven through its unit on
2026-11-25 at 13:50: all five rows `ok`, `ExecMainStatus=0`.

`check-pbx-sso.py` reads that schedule, since a monthly timer that stopped is invisible
for a month: the timer has to be enabled and active, and the drill's last run clean and
less than five weeks old. Exit 3 from the drill is the case that needs a person at once —
the name it broke is still pointing at a dead port — and it is reported as a failed run
here as well.

The four LAN rows are measured from `--lan-host` (default `192.168.1.54`), not from the
edge. `gui_auth.php` treats the edge's own address as the authenticated SSO path and
answers it with the "Sign-in is managed by Cerulean Authentik" 403 whatever the flag says,
so a probe *from the edge* reports the LAN door as broken from the one address it
deliberately never serves — which is exactly how the first scheduled run failed at 13:48
before the probe host was made a parameter. `--lan-host local` keeps the old
loopback-only behaviour for a run made on the PBX itself.

## Music on hold is published from the console's volume (2026-11-25)

The console warned that `/var/lib/asterisk/moh` did not hold the class audio, so pointing
Asterisk there would play silence. Both halves of that were true: the console's classes
live in its own volume (`…-pbx-data/media/moh/<class>`), and `publishMohPath()` calls a
class *published* only when its audio is readable at `MOH_PUBLISH_DIR`
(`/var/lib/asterisk/moh` by default); FreePBX's `/var/lib/asterisk/moh` meanwhile held the
stock `asterisk-moh-opsound-*` files and no `default/` or `jazz/` subdirectory.

What is in place now — all of it in Coolify's **stored** definition for the two services
(`deploy.innotel.us`, API at `192.168.1.85:8000`), so a redeploy carries it:

| where | mount | why |
| --- | --- | --- |
| FreePBX `qvifit…` | `…/jbtp…-pbx-data/_data/media/moh` → `/var/lib/asterisk/moh:ro` | Asterisk reads the console's audio at the stock path |
| FreePBX `qvifit…` | the same directory → `/data/media/moh:ro` | so the file the console *generates* (`/data/media/moh/<class>`) is readable too, not only the classes below |
| FreePBX `qvifit…` | `/opt/innotel/pbx/gui_auth.php` → `/var/www/html/admin/libraries/gui_auth.php:ro` | the SSO shim, which now survives a recreate |
| Console `jbtp…` | env `MOH_PUBLISH_DIR=/data/media/moh` | the console's own store *is* its publish directory, so its warning is about a path that exists |

Asterisk's classes come from `/etc/asterisk/musiconhold_console.conf` in the
`asterisk-config` volume, included **after** `musiconhold_additional.conf` in
`musiconhold.conf` — FreePBX's own `[default]` points at `/var/lib/asterisk/moh`, which
is now a directory of class subdirectories, and `mode=files` would play silence over it:

    [default]  mode=files sort=alpha directory=/var/lib/asterisk/moh/default
    [jazz]     mode=files sort=alpha directory=/var/lib/asterisk/moh/jazz

Verified 2026-11-25 18:44-18:50: `moh show classes` lists both with those directories,
`moh show files` lists one file per class from the console's volume, and the console's own
`GET /api/config` returns `warnings: []` (it emitted the "not published" line before).

**Why the console has no bind mount of its own**: Coolify's application API accepts only
`persistent` storage (a volume it names from `name`), refuses `host_path`, and its deploy
rejects `-v` in `custom_docker_run_options` ("not supported and were not applied"). Making
the console's store its publish directory is the supported equivalent, and the FreePBX
side mounts that same directory at both paths so either form of the generated config is
readable.

Reload after changing either file:

    docker exec freepbx-… asterisk -rx "module reload res_musiconhold.so"
    docker exec freepbx-… asterisk -rx "moh show classes"
    docker exec freepbx-… asterisk -rx "moh show files"

The module is `res_musiconhold.so`; `app_musiconhold.so` does not exist on this image.

### Watching it

`scripts/check-pbx-moh.py` fails when any of this drifts, and it reads the two containers
rather than a description of them:

- FreePBX still mounts the console's media directory at `/var/lib/asterisk/moh` (a note
  if `/data/media/moh` — the path the console's generated config names — is not mounted);
- every class `moh show classes` names reads a directory **under** that mount, and that
  directory holds at least one readable, non-empty file inside FreePBX — `mode=files`
  pointed at the mount itself plays silence over the class subdirectories;
- `moh show files` names at least one file for every class, which is the list Asterisk
  actually plays from;
- every class with audio in the console's own publish directory has an Asterisk class. A
  published class nothing plays is exactly the silence the console used to warn about.

It is listed in `estate-checks.service` as `pbx_moh`, so `EstateCheckAbsent`,
`EstateCheckFailing` and `EstateCheckNotRunning` cover it and the `Checks reporting`
panel counts it. A mount dropped from Coolify's stored compose is now a red check rather
than a caller asking why the hold music stopped.

## The console's AMI settings cannot be reset by an update (2026-11-25)

The console keeps `ami_host`/`ami_port` in its own SQLite volume, and its start-up
migration writes the image's seed values over them (`freepbx`, on a network the console
cannot resolve), which on the page reads exactly like a connection that is merely down.
It reads no `AMI_*` environment variable at all, so compose cannot pin it.

`scripts/ensure-console-ami.py` reads the console's admin password from its container over
ssh (never from the repository), logs in the way the page does, and writes `ami_host` and
`ami_port` only when they are wrong — nothing else, and never the manager credential.
`systemd/console-ami-pin.timer` runs it every ten minutes and three minutes after boot on
the edge. First run: `ensure-console-ami: … ami_host=192.168.1.52, ami_port=5038
(unchanged)`.

It is a reconciler, not the alarm: `check-pbx-console.py` still asserts the link is live
and publishes the textfile the rules read, so a reset that this job could not repair shows
up there within one check interval. That check also reads the timer itself —
`console-ami-pin.timer` enabled and active, its last run clean and less than two hours old
(it fires every ten minutes) — because a reconciler that stopped is the one failure with
no symptom until the next image update resets the settings again.

The four units and their two scripts are installed by `scripts/install-estate-checks.sh`
with the checks: they are listed in `COMPANION_UNITS`/`COMPANION_SCRIPTS` there, installed
from the same checkout under the same guard, and `--verify` holds them to `origin/main` the
same way. A unit installed without its script is `203/EXEC` on a schedule nobody is
watching, which is precisely what installing them by hand invited. Fresh host:

    sudo bash scripts/install-estate-checks.sh
    sudo systemctl enable --now console-ami-pin.timer pbx-breakglass-drill.timer

`check-unit-drift.py` compares installed units to this revision, so an edit here that is
not installed shows up in `estate_unit_drift` rather than silently not running.

## Operating notes

- **Adding a PBX administrator**: put the person in the `authentik Admins` group
  in Authentik. No FreePBX change is needed, and nothing in `gui_auth.php`
  changes. To give one person access without the group, add
  `'their-username' => 'admin'` to `sso_identities.php`.
- **If a FreePBX framework update overwrites `gui_auth.php`**, the password form
  comes back on the edge. The marker that the SSO block is present is the string
  `Sign-in is managed by Cerulean Authentik`; `check-pbx-sso.py` asserts it.
- **A redeploy that pulls a newer `pbx-portal` image no longer takes the shim with it**
  (measured 2026-11-25 18:18, before the mount: the image digest changed and
  `gui_auth.php` came back as the stock 4086-byte framework file). The container now
  mounts `/opt/innotel/pbx/gui_auth.php` read-only over
  `/var/www/html/admin/libraries/gui_auth.php`, so the file on the PBX host *is* the shim
  and both a framework upgrade and a recreate leave it alone. Editing the host file is
  live on the next request; `check-pbx-sso.py` still asserts the SSO marker is present,
  which is what would catch the mount disappearing from Coolify's stored compose. If that
  ever happens, the interim restore is `docker cp` + `chown asterisk:asterisk` +
  `chmod 664`, and the public names stay behind the edge's gate meanwhile — the symptom is
  a second password prompt, not an open door.
- **Do not move `location /admin` back to server level** in the NPM advanced
  config; nginx will ignore the headers. `check-pbx-sso.py` asserts the five headers
  are inside the block and the gate is outside it.
- **Do not remove the session guard** on the break-glass 403; without it a
  successful SSO sign-in is refused.
- `voice.innotel.us` continues to use its own `Voice NPM Forward Auth` provider;
  the others use their zone's provider. Both set the same user headers.
