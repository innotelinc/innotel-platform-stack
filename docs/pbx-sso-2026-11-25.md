# FreePBX administration now signs in with Cerulean Authentik — 2026-11-25

The FreePBX 17 administration GUI no longer asks for a FreePBX password on any public
name, and there is no standing password form on the container's port either. A request
on the edge is authenticated by Authentik, and the identity Authentik establishes is
what FreePBX uses. The only way to see the local form is for root to arm a flag inside
the container, and that flag lives in tmpfs.

## Why it was not working before

Two faults, either of which alone would have shown the password form:

1. `voice.innotel.site` forwarded to `192.168.1.52:8201`, a port nothing has ever
   listened on. The Authentik gate passed, and the post-login request died
   upstream. Fixed first (now `:8083`, the FreePBX Apache).
2. The gate authenticated but never passed the identity. NPM writes
   `advanced_config` at **server** level, and its generated `location /` sets its
   own `proxy_set_header` lines, so nginx does not inherit the server-level
   `X-authentik-*` headers into the location. FreePBX's SSO shim therefore saw
   no user at all and fell through to its login form. This affected every host
   using the managed gate, not just the PBX.

## What FreePBX does now

`/var/www/html/admin/libraries/gui_auth.php` (in the `freepbx-www` volume) reads
the identity the edge forwarded and opens the GUI without a password:

- A username in `sso_identities.php`'s `users` map, or a member of a group in its
  `groups` map, is opened as that FreePBX account. The maps currently resolve
  `dhunter` and every member of `authentik Admins` (`akadmin`, `dhunter`, `admin`)
  to the FreePBX `admin` account.
- A request that arrives **from the edge** with no identity, or with one that maps
  to nothing, gets a 403 page that names Authentik and the group to ask for. It
  does **not** get the password form.
- A request that arrives on the container's own address is untouched by the SSO
  block, but the password form is no longer a standing door there either (see
  *Break-glass* below).
- All the SSO code only runs when `REMOTE_ADDR` is the NPM edge (`192.168.1.71`).

The 403 that refuses an unmapped identity must be guarded by
`empty($_SESSION['AMP_user'])`. Without that guard the shim authenticates the request,
sets the session, and then 403s it anyway — a total lockout that looks exactly like
"no identity arrived". That mistake was made and fixed on 2026-11-25, and
`scripts/check-pbx-sso.py` now asserts the guard is still there.

### Break-glass

The stock password form is reachable only when root arms a flag inside the container:

```sh
docker exec freepbx-qvifit87vftfxd9ejsch2vxy touch /run/freepbx-sso-break-glass
# ... sign in on http://192.168.1.52:8083/admin/config.php ...
docker exec freepbx-qvifit87vftfxd9ejsch2vxy rm -f /run/freepbx-sso-break-glass
```

`/run` is the container's tmpfs, so a restart disarms it. Leave it disarmed: the
drift check warns when it is armed, because an armed flag is a password door open to
the LAN.

Backups from this change, beside the file: `gui_auth.php.bak-sso-edge-20261125` (the
first SSO version, with the form), `gui_auth.php.bak-sso-nopw-20261125` (form removed,
but the 403 was unguarded — the lockout), and
`gui_auth.php.bak-sso-breakglassguard-20261125` (immediately before the guard fix).

### `pbx.innotel.site` uses its own outpost

The other names use their domain's zone provider. `pbx.innotel.site` cannot: the zone
provider (`Innotel.site Zone`, provider 69) is a domain-level provider for
`*.innotel.site`, and it shadows every single-application provider for that name no
matter how the outpost provider list is ordered. Domain mode also cannot enforce a
per-application policy — Authentik only applies bindings in single-application mode.

So the console has both:

- provider **73** `Innotel PBX Console NPM Forward Auth` (`forward_single`,
  `external_host https://pbx.innotel.site`, `internal_host http://192.168.1.52:8097`)
  and app `innotel-pbx-console`, bound to `authentik Admins` (binding
  `8067566f-1d03-484a-86dc-ad83804c39a7`);
- a dedicated external outpost, container `authentik-pbx-outpost` on `192.168.1.71`
  (`ghcr.io/goauthentik/proxy:2026.8.6`, network `proxy_default`, no published
  ports), which carries **only** provider 73. NPM host 410 points its
  `/outpost.goauthentik.io` location and its sign-in redirect at that outpost.

That separation is what makes the group binding effective: a signed-in user outside
`authentik Admins` is refused at the authorize page, and an admin gets the console.

The outpost's API token is at `192.168.1.71:/root/.authentik-pbx-outpost-token`
(600, identifier `ak-outpost-fbd22a38-8b46-49a9-9b99-ac46c51d1f9b-api`). If the
container is lost, recreate it from that token rather than making a new outpost —
provider 73 and NPM refer to it by outpost identity.

## `:8083` is LAN-only

The published port is still how the edge reaches FreePBX, and it is also the
break-glass address. It is filtered on the PBX host (`192.168.1.52`) in **`raw
PREROUTING`**:

```
-A PREROUTING -s 192.168.1.0/24 -p tcp --dport 8083 -j RETURN
-A PREROUTING -s 127.0.0.0/8    -p tcp --dport 8083 -j RETURN
-A PREROUTING -p tcp --dport 8083 -j DROP
```

`raw PREROUTING` rather than `DOCKER-USER`: by `DOCKER-USER` the published port has
already been DNATed to the container's `:80`, so `--dport 8083` no longer matches and
a rule there silently allows everything. The rules are written by
`/usr/local/sbin/capstone-wan-acl.sh` and re-applied by the enabled one-shot
`capstone-wan-acl.service`, so a reboot restores them.

## Verified

- A temporary Authentik user (created, used, deleted) signed in through the real flow
  at `auth.innotel.us`, then loaded `https://voice.innotel.site/admin/config.php`:
  **200**, FreePBX Administration, no password form.
- The same flow with the user **not** in `authentik Admins`: **403**, the "no
  administration account mapped" page, no form.
- Anonymous requests to every gated name: **302** to that name's Authentik outpost.
- `https://pbx.innotel.site/` for an admin in `authentik Admins`: **200**, Asterisk
  Console; a signed-in non-admin is refused at the authorize page.
- Direct `http://192.168.1.52:8083/admin/config.php`: **403** ("PBX password sign-in
  is disabled"). With the break-glass flag armed: **200** with the local form. Flag
  removed: **403** again.
- `nginx -t` on the edge: successful.
- `voice.innotel.us` reaches its provider's authorize page (that provider uses an
  explicit consent flow, so the automated probe stops there; the GUI block is the
  same as the verified host).
- `scripts/check-pbx-sso.py`: all eight assertions pass.

## Watching it

`scripts/check-pbx-sso.py` fails when any of this drifts. It reads NPM's rows (not the
files NPM regenerates), the shim inside the FreePBX container, and `raw PREROUTING` on
the PBX host:

```sh
./scripts/check-pbx-sso.py                       # on the edge
./scripts/check-pbx-sso.py --npm-url http://192.168.1.71:81 \
    --token-file /root/.npm-token --pbx 192.168.1.52 --ssh-key /root/.ssh/id_ed25519
```

Exit 0 = everything holds, 1 = drift, 2 = a host could not be read. It is listed in
`estate-checks.service` as `pbx_sso` and publishes the shared `innotel_estate_check_*`
family, so `EstateCheckAbsent`, `EstateCheckFailing` and `EstateCheckNotRunning` cover it
and the `Checks reporting` panel counts it. It installs with the unit, from `main` —
`check-installed-checks` compares the directory against `origin/main`, so installing it
ahead of the merge is itself reported as drift, and is what that alarm is for.

## Break-glass drill (2026-11-25)

The gate was made unreachable for one name only: `pbx.telno.services`'s
`/outpost.goauthentik.io` location was pointed at a closed port (`127.0.0.1:9`) through
the NPM API, measured, and put back. Every other name kept its own outpost throughout.

| what was tried | what came back |
| --- | --- |
| `https://pbx.telno.services/admin/config.php`, gate unreachable | `500` — no password form, no FreePBX page |
| `http://192.168.1.52:8083/admin/config.php`, flag absent | `403` |
| same, with `/run/freepbx-sso-break-glass` touched | `200`, the FreePBX password form |
| same, flag removed again | `403` |
| gate restored, anonymous request | `302` to Authentik |

So an unreachable outpost fails closed: the edge answers `500`, never the form, and the
only way in is the LAN flag that `check-pbx-sso.py` asserts is off. `500` is ugly; it is
also the only status nginx can return when an `auth_request` subrequest cannot be made,
and it is strictly better than a login prompt. The LAN path was proven on the PBX host
itself, which is what "the edge is down" leaves a person with.

## Operating notes

- **Adding a PBX administrator**: put the person in the `authentik Admins` group
  in Authentik. No FreePBX change is needed, and nothing in `gui_auth.php`
  changes. To give one person access without the group, add
  `'their-username' => 'admin'` to `sso_identities.php`.
- **If a FreePBX framework update overwrites `gui_auth.php`**, the password form
  comes back on the edge. The marker that the SSO block is present is the string
  `Sign-in is managed by Cerulean Authentik`; `check-pbx-sso.py` asserts it. Keep
  the volume, not just the container.
- **Do not move `location /admin` back to server level** in the NPM advanced
  config; nginx will ignore the headers. `check-pbx-sso.py` asserts the five headers
  are inside the block and the gate is outside it.
- **Do not remove the session guard** on the break-glass 403; without it a
  successful SSO sign-in is refused.
- `voice.innotel.us` continues to use its own `Voice NPM Forward Auth` provider;
  the others use their zone's provider. Both set the same user headers.
